# v0.5 Deterministic Baseline - Benchmark Evolution

**Date**: 2026-05-09
**Version**: v0.5
**Status**: FROZEN - Deterministic baseline, no further algorithm tuning

---

## Executive Summary

Three consecutive algorithm tuning iterations (v0.3, v0.4, v0.5) produced **no measurable improvement** in benchmark hit rates. This is a meaningful null result.

**Conclusion**: Retrieval algorithm tuning is not the bottleneck. Signal coverage and query-to-symbol semantic mapping are the bottlenecks.

| v0.4 | +chain-aware reranking | 33.3% | 40% | 80% | 100% |

---

## v0.4: Chain-Aware Reranking

**Hypothesis**: Signals connected by graph edges should be boosted together.

**Implementation**:
- Added `findConnectedSignals()` to trace graph adjacency
- Added `computeChainScore()` to score signal clusters
- Integrated chain score into hybrid search ranking

**Outcome**: No measurable gain.

**Analysis**: Chain-aware reranking cannot help when the primary signal itself isn't retrieved. The failure is at the signal-existence level, not ranking level.

---

## v0.5: Semantic Normalization

**Hypothesis**: Query terms like "chat" should match signal "completion" via semantic expansion.

**Implementation**:
- Added `SIGNAL_TERM_MAPPING` dictionary (serializers→serializer, views→view, etc.)
- Added `DOMAIN_TERM_NORMALIZATION` (api/rest→endpoint, routers→router)
- Added `normalizeQueryTerm()` and `normalizeSignalTerm()` functions
- Enhanced `extractQueryIntent()` to apply normalization during expansion

**Outcome**: No measurable gain.

**Analysis**: Normalization helps when query terms are lexically close to signal terms but differ in singular/plural form. It cannot help when the query concept (chat) is semantically distant from the indexed signal (completion).

## Failure Analysis

### LiteLLM (10 failures, 9 `missing_graph_edge`, 1 `missing_signal_kind`)

**Query "Find the chat completion implementation"** expects signal with "chat" in file path.
- Signal `completion` exists in `index.ts`
- Signal `completionStream` exists with "chat" semantic meaning but not in filename
- `fileContains: "chat"` check fails because no signal has "chat" in its file path

**Root Cause**: Query expects `fileContains: "chat"` but signal files are named `index.ts`, `providers/openai.ts`, etc. The semantic concept "chat" is not encoded in any signal's file path.

**Evidence**: Signal text says "chat completion" but file path doesn't contain "chat".

### DRF (9 failures, 8 `missing_signal_kind`, 1 `missing_graph_edge`)

**Query "Show me the router configuration"** expects a signal with `kind: "file"` or router configuration.
- Signals include `UserViewSet`, `PostViewSet`, `PostPagination` (all class-based)
- No signal with `kind: "file"` or router configuration exists

**Root Cause**: The fixture is missing signals for router configuration. The query expects something that doesn't exist in the signal index.

**Evidence**: All DRF signals are classes/functions. No file or configuration signal for router.

### FastAPI (3 failures, 1 `query_too_semantic`, 2 `lexical_mismatch`)

**Query "Find the password reset implementation"** expects semantic match.
- Signal `resetPassword` exists but query fails to match
- Query uses "password reset" but signal is `resetPassword`

**Root Cause**: Query-to-symbol mapping fails even though the concept exists. This is closer to a legitimate algorithm gap, but fixing it requires embeddings-level semantic matching.

## Honest Characterization

### Context Signals Works Well When:
1. **Structural signals exist**: Function names, classes, routes that directly match query terms
2. **Query terms map to indexed symbols**: "OpenAI provider" → `OpenAIProvider` signal
3. **File paths contain relevant keywords**: Query for "middleware" matches signal with `file: "middleware/index.ts"`

### Context Signals Is Weak When:
1. **Required concept is absent from signals**: Query expects router config but fixture has no such signal
2. **Query uses semantically different terms**: "chat completion" vs. "completion"
3. **File paths don't encode the concept**: "chat" not in any filename, but query expects it
4. **Semantic gap between query and indexed name**: "password reset" vs. "resetPassword"

## Decision: Freeze v0.5

**v0.5 is now the deterministic baseline.** No further retrieval algorithm tuning will occur.

**Rationale**:
1. Three iterations produced zero measurable gain
2. The bottleneck is fixture coverage, not algorithm quality
3. More algorithm tuning without fixture expansion is wasted effort

---

## Next Step: v0.6 Embeddings Experiment

**Positioning**: Not a fix for CS - an optional semantic fallback when lexical+graph signals are insufficient.

**Design**:
- Primary retrieval remains BM25 + graph (deterministic)
- Embeddings used only as optional reranker on top-k results
- Local embeddings only (no external API dependency in v0.6)

**Proposed Flow**:
```
BM25 + graph → top 20 results
Local embeddings rerank top 20 → top 5
Return top 5
```

**Metrics to Track**:
- LiteLLM hit rate improvement
- DRF hit rate improvement
- Latency increase (ms per query)
- Index size increase (MB)
- Stability across runs (determinism)

**Decision Rule**: If LiteLLM/DRF improve by <15% with acceptable latency, embeddings stay optional/off. If >20% improvement with acceptable cost, offer as optional toggle.

## Conclusion

**Context Signals is strong when the right structural signals exist. It is weak when the required concept is absent or semantically distant from indexed symbols.**

This is a good engineering finding. It clarifies the actual problem domain for CS:
- **Good fit**: Projects with well-named functions, explicit file structure, clear routes
- **Poor fit**: Projects where concepts are隐晦ly encoded or query terms diverge from symbol names

The v0.5 freeze provides a stable baseline. The v0.6 embeddings experiment will quantify whether semantic fallback can extend coverage without breaking the deterministic nature of the primary retrieval path.
