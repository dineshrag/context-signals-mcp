1. Abstract

Coding agents spend a significant portion of their context budget on repository navigation—searching for files, inspecting irrelevant modules, and repeatedly discovering architectural structure across sessions. We introduce Context Signals MCP, a lightweight repository context layer that extracts compact structural signals from source code and exposes them via the Model Context Protocol (MCP).

The system extracts structured representations including functions, classes, routes, imports, and call edges, storing them in a local SQLite database indexed for fast retrieval. An MCP server exposes tools (signals_search, signals_scan, signals_stats, signals_ingest) that allow coding agents to navigate via metadata before reading source files.

Core Claim

Structured signal extraction reduces the token cost of navigation queries by 51–95%, with strongest gains on architectural and multi-hop queries.

Evaluation Scope

Retrieval benchmarks across LiteLLM (TypeScript) and historical runs on Flask, FastAPI, Django REST Framework. Seven iterations (v0.2–v0.8) over 4 months. The repo ships with the LiteLLM fixture only.

Key limitation: Context Signals is not a replacement for semantic code understanding. It is a navigation layer that reduces unnecessary file reads. Deep implementation reasoning still requires reading source code.

2. Problem Statement

Coding Agent Navigation Waste

When a coding agent needs to answer a question like “Where is the POST /upload route?”, it typically follows a costly pattern:

1
Semantic grep
Agent searches across the codebase with grep or similar tools, returning partial or overly broad matches.
2
Open multiple files
Agent opens candidate files entirely, reading thousands of tokens of irrelevant code.
3
Send to LLM
Sends entire file contents to the LLM, consuming context window for structural discovery.
4
Repeat
If the file was wrong, the cycle repeats. Same structure discovered again next session.

This pattern produces:

  • Token waste — 5–15K tokens per navigation query on large codebases (Trigger.dev: 39,904 tokens for a single API client auth query)
  • Latency — Multiple round-trips to read files before the LLM can answer
  • Context exhaustion — Structural discovery competes with reasoning for limited context window
  • Repeated cost — Same navigation repeated across sessions with no reuse
Without Structured Retrieval
  • 10+ files opened per navigation task
  • Repeated grep loops across directories
  • Duplicated reads of the same files
  • No cross-session memory
With Structured Retrieval
  • 1–3 candidate files from signal store
  • Graph-guided exploration reduces search
  • Compact signal payload (~400 chars) vs full file reads (~2000+ chars)
  • Persistent cache across sessions

3. System Design

Figure 1: High-level system architecture showing the five-component pipeline from coding agent to storage layer.

3.1 Extraction Layer

The extraction engine uses a language-adapter pattern for extensibility. Each language registers an LanguageAdapter that implements:

interface LanguageAdapter {
  language: string;
  canExtract(file: string): boolean;
  extract(content: string, file: string): Promise<ExtractResult>;
  init?(): Promise<void>;
  destroy?(): void;
}

interface ExtractResult {
  signals: Signal[];     // functions, classes, routes, imports, exports
  calls: CallEdge[];     // call edges (fromFile:fromSymbol → toRaw:toResolved)
  imports: ImportEdge[]; // import graph edges
  errors: string[];
  language: string;
  isReactComponent: boolean;
  detectedFrameworks: string[];
}
TS / JS Extraction
  • TypeScript Compiler API walker
  • Functions, classes, interfaces, types
  • Imports, exports, decorators
  • Built-in filter excludes: console, JSON, Math, HTTPException, etc.
Python Extraction
  • Regex-based PythonAdapter
  • Function definitions, class definitions
  • Import statements, decorators
  • Call edge inference
Framework Detection
  • Express: app.get/post/put/delete/router
  • Fastify: fastify.get/post/route()
  • Next.js: app/api/route.ts, pages router
  • React: Uppercase function components

3.2 SQLite Architecture

We chose SQLite (via sql.js) as the primary storage backend for several reasons:

  • Reproducibility — the database file is a single artifact that can be archived, versioned, and replayed
  • Structured queries — SQL enables precise filtering by kind, file, framework, language
  • Benchmark replay — fixed signal snapshots enable deterministic benchmark execution
  • Relational traversal — JOINs across signals, call_edges, and import_edges enable graph queries
  • Low overhead — no external database process; single-file persistence
Figure 2: Core SQLite schema showing the three primary tables for signals, call edges, and import edges. Additional tables for benchmark_runs and benchmark_results support evaluation replay.

3.3 Retrieval Pipeline

Figure 3: The multi-stage retrieval pipeline from query intent extraction through hybrid scoring and deduplication.
Deterministic Retrieval (Default)
  • BM25 via MiniSearch on text, name, file, tags fields
  • Name boost: ×4, Tags boost: ×3, File boost: ×2
  • LexicalBoost: fuzzy matching with stemming (name: ×3, file: ×2)
  • GraphScorer: call edge traversal, chain depth scoring
  • LocalityScorer: directory proximity to recent files
  • Hybrid combiner: weighted sum (BM25 0.4, Graph 0.3, Metadata 0.2, Locality 0.1)
Optional Embedding Mode
  • Model: Xenova/all-MiniLM-L6-v2 (384 dimensions, ~90MB)
  • Architecture: rerank-only on BM25+graph top-20 candidates
  • Blend: 0.3 embedding score + 0.7 original score
  • Disabled by default per decision rule
  • Rationale: low added cost, deterministic baseline preserved, semantic fallback only

4. Benchmark Design

Our benchmark methodology follows a benchmark-first development philosophy: frozen fixtures, consistent scoring weights, and identical retrieval logic across all frameworks. We prefer honest degradation over overfitting to specific project patterns.

5. Benchmark Evolution

The benchmark suite evolved through seven iterations (v0.2–v0.8) across four months. Below is the evolution timeline and key findings at each stage.

Figure 4: Benchmark evolution timeline showing hit rate progression and key findings at each version. Three consecutive algorithm tuning rounds (v0.3–v0.5) produced 0% improvement.

v0.3: Initial Retrieval Baseline

Established the BM25 baseline with graph scoring. Validated that structured signal extraction provides measurable context reduction (51–73% across projects). Hit rates: Flask 100%, FastAPI 80%, DRF 40%, LiteLLM 33%.

v0.4: Chain-Aware Reranking

Added call-edge graph traversal to reranking. Result: no measurable improvement across any project. Key insight: ranking is not the primary bottleneck—signal coverage is.

v0.5: Semantic Normalization

Applied synonym expansion and term normalization. Result: negligible benchmark change. Failures were caused by missing signal coverage, not scoring accuracy. Frozen as deterministic baseline.

§ v0.5 Freeze Decision

Three consecutive algorithm tuning rounds produced 0% improvement. The bottleneck is signal coverage and query-to-symbol semantic mapping, not scoring algorithm sophistication. No further retrieval algorithm tuning.

v0.6: Optional Embedding Experiment

Tested Xenova/all-MiniLM-L6-v2 as an optional reranker on BM25+graph top-20 candidates. Results:

7. Failure Analysis

We analyzed all missed queries across the benchmark suite to identify failure categories:

Figure 5: Distribution of failure modes across all benchmark queries. Missing signal coverage (38%) is the dominant failure mode.
1. Missing Signal Kind (38%)

The target entity was not extracted as a signal. Common causes: unsupported language features, deeply nested definitions, or dynamic constructs that static analysis cannot resolve. Signals are structural, not exhaustive.

2. Missing Graph Edge (24%)

The call edge or import edge connecting the query to the target was not captured. Inferred edges have lower confidence. Dynamic dispatch and cross-module references are particularly challenging.

3. Semantic Mismatch (22%)

The query terms did not match any signal text, name, or tags. Example: querying for "chat completion" when the signal uses "inference" or "generate". Embeddings help here but are optional.

4. Sparse Coverage (16%)

The codebase has too few signals relative to its size, or the query targets implementation details below the signal extraction threshold. Most common in class-heavy frameworks.

8. Key Insights

Most Important Finding

Context Signals is not a universal replacement for repository search. Its strongest value appears in semantic-heavy repositories where architectural navigation requires understanding provider dispatch, configuration merging, and multi-hop relationships. On simple, grep-friendly codebases, the improvement is marginal.

Insight 1: Scoring Is Not the Bottleneck

Three consecutive algorithm tuning rounds (v0.3→v0.5) produced 0% improvement. The bottleneck is signal coverage, not scoring sophistication. Better extraction > better scoring.

Insight 2: Graph Structure Adds Value

Call edges and import edges enable graph-aware scoring that captures architectural relationships. LiteLLM's 27% file-open reduction in v0.7 is driven by graph-guided navigation.

Insight 3: Embeddings Are a Surgical Tool

Embeddings help when lexical mapping fails (LiteLLM: +26.7%), but they do not solve missing signals or missing graph edges. Keep them optional, use them surgically.

Insight 4: Precision Over Speed

Context Signals improves navigation by returning more relevant targets (higher ground truth found rate), not necessarily fewer files. The value is in avoiding wrong-file exploration.

9. Limitations

Evaluation Scale
  • 4 Python projects + 3 TypeScript fixtures
  • 15 queries per project (60 total)
  • Limited real-agent validation
  • v0.8 partially blocked by CLI/TTY constraints
Extraction Quality
  • Retrieval quality depends on extraction quality
  • Python extraction is regex-based, not AST
  • Dynamic constructs cannot be statically analyzed
  • Deeply nested definitions may be missed
Semantic Understanding
  • No semantic understanding without embeddings
  • Query terms must lexically overlap with signals
  • Synonym expansion is manually maintained
  • Cross-language semantic gaps exist
Platform Constraints
  • v0.8 agent benchmark requires WSL on Windows
  • Python extraction has no native AST support
  • Large repos may have slow initial indexing
  • File size cap: 10 MB

11. Conclusion

This evaluation demonstrates that structured repository signals can reduce navigation waste in coding agents by 51–95% for retrieval queries, with the strongest gains appearing in architectural and semantic-heavy codebases.

Key conclusions:

Deterministic retrieval remains the preferred default. Algorithm tuning (v0.3→v0.5) produced 0% improvement—the bottleneck is signal coverage.

Embeddings are useful as an optional semantic fallback. LiteLLM: +26.7% hit rate. Disabled by default to preserve zero-dependency operation.

Navigation precision is the primary mechanism. CS achieves higher ground truth found rate (94% vs 88%) through more targeted file suggestions, not necessarily fewer opens.

Final Positioning

Context Signals MCP is best viewed as a lightweight repository navigation layer designed for coding-agent context efficiency. It reduces unnecessary repository exploration by providing a compact, reusable map of codebase structure. It does not replace semantic code understanding or implementation reasoning—it ensures agents spend their context budget on the right code.
