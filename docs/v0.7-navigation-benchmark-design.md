# v0.7 Navigation Outcome Benchmark

**Date**: 2026-05-09
**Version**: v0.7
**Focus**: Measure whether MCP reduces navigation work before LLM involvement

---

## Motivation

v0.6 retrieval benchmark showed CS improves hit rate on semantic-heavy repos (LiteLLM +26.7%). But retrieval metrics don't prove MCP helps real agent workflows.

**v0.7 purpose**: Measure navigation efficiency - how much work is reduced before LLM makes a decision.

---

## Framing Correction

**Do NOT call it "agent simulator"** - industry will challenge "programmatic simulator is not a real agent."

**Correct framing**: Navigation Outcome Benchmark

It measures whether MCP reduces navigation work before involving LLM variability. Clean separation:
- v0.7 = Navigation harness (no LLM)
- v0.8 = Real agent task benchmark (with LLM)

---

## Design

### Two Navigation Modes

**Baseline (grep/search)**:
1. Parse query → extract search terms
2. Run grep across all files
3. Rank by matches
4. Open files sequentially until ground truth found
5. Stop when expected file found or max attempts reached

**Context Signals**:
1. Parse query → extract search terms
2. Call `context_signals.search` with terms
3. Open only returned target files
4. Stop when expected file found or results exhausted

---

## Metrics Tracked

| Metric | Description |
|--------|-------------|
| `fileOpens` | Number of files opened during navigation |
| `charsRead` | Total characters read from files |
| `searchCalls` | Number of search operations (grep or CS search) |
| `wrongFilesOpened` | Files opened that don't contain target |
| `stepsToGroundTruth` | Number of file opens to reach correct answer |
| `topKSuccess` | Whether correct file appears in top-k results |
| `timeMs` | Total navigation time |
| `contextReduction` | Baseline chars / CS chars |

## Task Definition Format

```json
{
  "taskId": "litellm-005",
  "repo": "litellm",
  "goal": "Find where model configuration is merged before provider dispatch",
  "query": "Where is model config merged before being sent to provider?",
  "expectedFiles": ["providers/config.ts"],
  "expectedSymbols": ["mergeConfigs"],
  "successCriteria": {
    "minExpectedSymbolsFound": 1,
    "maxWrongFiles": 3,
    "maxFileOpens": 5
  }
}
```

---

## Task Types

Use navigation tasks that represent real agent queries:

1. **Lookup**: "Find where login is handled"
2. **Trace**: "Trace user registration flow"  
3. **List**: "Find all API routes"
4. **Locate**: "Find where provider config is merged"
5. **Find**: "Find password reset implementation"
6. **Discover**: "Find middleware used in auth"

---

## Benchmark Flow

```
For each project (flask, fastapi, drf, litellm):
  For each task:
    1. Run baseline navigation
       - Record all file opens
       - Record chars read
       - Record steps to ground truth

    2. Run CS navigation
       - Record only returned targets opened
       - Record chars read
       - Record steps to ground truth

    3. Compare outcomes
```

---

## Decision Criteria

- If CS reduces file opens by >30% vs baseline → strong signal
- If CS reduces steps to ground truth by >40% → strong signal  
- If CS achieves >80% top-5 success rate → strong signal
- If baseline navigation already efficient (<3 file opens) → ceiling effect

---

## v0.7 vs v0.6 Distinction

| Version | What it measures | LLM involved? |
|---------|------------------|---------------|
| v0.6 | Retrieval hit rate | No |
| v0.7 | Navigation efficiency | No |
| v0.8 | Agent task completion | Yes |

v0.7 is purely mechanical - measures how quickly navigation reaches ground truth without LLM judgment in the loop.

---

## Expected Outcomes

**If CS helps navigation**:
- Fewer file opens to reach ground truth
- Higher top-k success rate
- Lower chars read per task

**If CS doesn't help navigation**:
- Same file open count as baseline
- Same steps to ground truth
- Retrieval improvement doesn't translate to navigation improvement

This distinction matters because a retrieval system could have high hit rate but still require opening many wrong files to verify.
